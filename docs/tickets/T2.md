# T2 — Several people share one canvas, each attributed by their own connection

**Status:** not-started
**Model:** gpt-5.6-luna @ max · **Escalate to:** gpt-5.6-sol @ xhigh
**Wave:** 1 · **Branches:** `ticket/T2`

## Context

Roomy turns live speech into a shared canvas. Read `CLAUDE.md` first, then the "Where
this is going" section of `BACKLOG.md`: each participant opens Roomy in their own browser
beside whatever call they are on, so one browser transcribes one person and **speaker
identity comes from the connection**. That is how Roomy gets diarization for free and
why it never needs to integrate with a meeting tool's audio.

Today `src/server.ts:11` creates one hardcoded `Room`, every route is unscoped
(`/events`, `/utterance`, … at `src/server.ts:41-82`), and the client sends whatever is
in a free-text "speaker" box. Nothing distinguishes participants.

## Problem

- One room for the whole process: two groups cannot use one server.
- Speaker is a free-text field per message (`public/index.html:41`), not an identity.
- No presence: nobody knows who is in the room.
- The server auto-listens on import (`src/server.ts:88`), so it cannot be tested in-process.

## Solution direction

**Routes.** `/r/<slug>` serves the page. `/` redirects (302) to `/r/<fresh slug>`. Every
existing route moves under the slug: `/r/<slug>/events`, `/utterance`, `/render-error`,
`/replay`, `/reset`. Slug regex `^[a-z0-9-]{3,40}$`; anything else is 404. A room is
created on first use of its slug. Generated slugs: six or more random lowercase
alphanumerics. Unguessable enough for a PoC — say so in a `ponytail:` comment rather
than building access control.

**Identity.** The client asks for a name once, keeps it in `localStorage`, sends it as
`name` on the SSE connection (`/r/<slug>/events?name=…`) and as `speaker` on every
`/utterance`. The server trusts it — `ponytail:` comment, upgrade path is a signed
session cookie. The speaker on an utterance is the name of the connection that sent it.
Do nothing cleverer.

**Presence.** `Room` tracks its subscribers' names and emits
`{ type: "presence", people: string[] }` (sorted, de-duplicated) whenever the set
changes. Add the variant to `ServerMsg` at `src/room.ts:12`. The client shows the
list somewhere quiet.

**Reaping.** A room with no subscribers for ten minutes is deleted from the registry and
its timer stopped (`Room.stop()`). Make the interval injectable so a test can use
milliseconds.

**Testability.** `src/server.ts` exports a function that creates and starts the server on
a given port (0 is fine) and returns something a test can close; it auto-listens only
when run directly (`process.argv[1]` ends with `server.ts`). Tests use `fetch` and read
SSE by hand from a `Response` body stream — no new dependencies.

**Replay** targets a slug: `/r/<slug>/replay`. Update `src/replay.ts` to take the slug as
`ROOMY_URL`'s path or a third argument; keep the `npm run replay` script working.

Latitude: how the name prompt looks, how presence is rendered, internal registry shape.
Not open: routes and message shapes above; no auth; no persistence; no lobby or room list.

## Acceptance criteria

- [ ] `GET /` redirects to `/r/<slug>`; `GET /r/<bad slug>` is 404
- [ ] Two SSE connections on one slug with names A and B each receive `presence` with `["A","B"]`; when A disconnects, B receives `["B"]`
- [ ] An utterance posted with speaker A appears on B's stream as an `utterance` message with speaker A
- [ ] A third connection on a different slug receives none of the above
- [ ] `/r/<slug>/replay` populates that slug's room only
- [ ] With a millisecond reap interval, a room with no subscribers disappears from the registry and its timer is stopped
- [ ] The page works with no name stored (asks once) and remembers it across reloads
- [ ] `npm run replay -- incident-review 12` still works against a running server
