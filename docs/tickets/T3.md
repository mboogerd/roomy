# T3 — The canvas moves while people speak, and never flickers

**Status:** not-started
**Model:** gpt-5.6-luna @ max · **Escalate to:** gpt-5.6-sol @ xhigh
**Wave:** 2 · **Branches:** `ticket/T3`

## Context

Roomy turns live speech into a shared canvas of mermaid diagrams. Read `CLAUDE.md`, then
`docs/pipeline.md` — twice. That document is the design; this ticket implements it.

Today `src/room.ts` drives the canvas from a timer: every `TICK_MS` it checks whether
`MIN_NEW_CHARS` of new transcript have arrived, sends a window of raw utterances to the
LLM, applies the ops (`maybeTick`, around line 66 — line numbers shifted slightly after
T1). The canvas updates at most every eight seconds and only after enough text
accumulates. There is no notion of a completed thought, no speculative rendering, and no
distinction between a settled canvas and a provisional one.

After T1, `Room` takes an LLM implementation as a constructor argument, has a public
single-tick method, and is covered by `test/scenarios.test.ts` with a stub in
`test/stub-llm.ts`. After T2, `Room` also tracks presence. Both are on `main`.

## Problem

- Latency: a thought is drawn up to eight seconds after it ends, never while it is being said.
- Windowing by character count ignores where thoughts begin and end; the model sees
  fragments of two thoughts or a tail without its head.
- Every update is committed as if final. There is no way to show a provisional edit and
  then settle it.

## Solution direction

Implement the journal from `docs/pipeline.md`: segments, stable snapshots, a replaceable
speculative overlay, one-in-flight speculation, commit on segment close, carry-forward
for short segments. **Not amend** — leave a `ponytail:` comment where it would go.

The three invariants in that document are the acceptance criteria. Everything else there
is guidance you should follow unless you find a concrete reason not to, which you then
state in your report.

Decided details:

- **Segment close**: a pause from the segment's speaker longer than `SEGMENT_PAUSE_MS`
  (default 1500), or an utterance from a different speaker, or the segment exceeding
  `SEGMENT_MAX_CHARS` (default 400). Pause detection uses a `setTimeout` reset on each
  utterance from the same speaker; tests use vitest fake timers.
- **Carry-forward**: a closing segment shorter than `SEGMENT_MIN_CHARS` (default 40) does
  not commit; its text is prepended to the next segment from the same speaker. If a
  different speaker arrives, the short segment commits anyway — better a fragment than
  a lost thought.
- **Speculate**: at most one speculative LLM call in flight; when it returns, if the live
  text has grown, fire again with the latest text. A result whose segment has already
  committed is discarded. The speculative prompt sees `stable[head]` and the live
  segment's text only. Add `buildSpeculatePrompt` to `src/prompt.ts` and `speculate` to
  the LLM interface in `src/llm.ts`, using `TICK_MODEL`.
- **Commit**: on close, compute ops from `stable[head]` + the segment, with the previous
  two committed segments as context, using the existing tick prompt. Apply, store the
  snapshot, clear the overlay. Memoize per segment.
- **What clients see**: `apply(stable[head], liveOps)`. The `state` message keeps its
  shape; add an optional `speculative: string[]` listing block ids that come from the
  overlay, so a client may style them. Clients that ignore the field behave correctly.
- **Restructure** (`RESTRUCTURE_EVERY`) counts commits, not ticks. **Summary**
  (`SUMMARY_EVERY`) likewise.
- Remove `TICK_MS`, `MIN_NEW_CHARS`, `setInterval`, and the raw-utterance window.
  `start()`/`stop()` may become no-ops but must still exist. The single-tick method from
  T1 becomes "close the live segment now and commit" — keep its name and awaitable
  contract so the scenario suite and eval harness keep working.
- `say()` and `subscribe()` keep their signatures.

Extend the eval summary (`src/eval.ts`) with: segments committed, segments carried
forward, speculative calls made, speculative results discarded as stale, and **the number
of segments where the same speaker resumed within 2 s of a commit** — that is how often
amend would have mattered; it decides whether amend gets built.

Latitude: internal data structures, how memoization is keyed, how the timers are
organised. Not open: the three invariants; one live segment per room (not per speaker —
`ponytail:` comment naming per-speaker heads as the upgrade); no delta computation
between op sets; no amend.

## Acceptance criteria

- [ ] Invariant 1: a test shows speculation never changes a stored snapshot
- [ ] Invariant 2: a test shows three consecutive speculations over the same live text leave an unchanged block with byte-identical source, and a changed speculation replaces rather than accumulates
- [ ] Invariant 3: a test shows the speculate and commit prompts receive the stable canvas, never the overlay
- [ ] Segmentation: tests for close-on-pause, close-on-speaker-change, close-on-length, and carry-forward of a short segment
- [ ] One-in-flight: with a stub that resolves on demand, a burst of five utterances during one in-flight call yields exactly one follow-up speculative call carrying the latest text
- [ ] Stale discard: a speculative result arriving after commit is not applied
- [ ] `test/scenarios.test.ts` still passes; `npm run eval` reports the new counters
- [ ] Eval reports for all three fixtures attached, including the amend-would-have-mattered count
