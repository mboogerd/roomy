# T1 — The pipeline is exercisable without voice, network, or a browser

**Status:** not-started
**Model:** gpt-5.6-luna @ max · **Escalate to:** gpt-5.6-sol @ xhigh
**Wave:** 1 · **Branches:** `ticket/T1`

## Context

Roomy turns live speech into a shared canvas of mermaid diagrams. Read `CLAUDE.md` first.
Transcript enters through `Room.say()` (`src/room.ts:40`), a timer-driven tick loop calls
the LLM (`src/room.ts:66` `maybeTick`), ops are validated and applied (`src/canvas.ts:41`,
`:77`), and subscribers receive full state (`src/room.ts:12` `ServerMsg`).

Today the only way to see the pipeline work is to run the server and replay a fixture
against the real Anthropic API. There are no tests of `Room` at all — `test/canvas.test.ts`
covers only the pure functions. Every later ticket needs to prove itself against the
pipeline, deterministically, from inside a container with no browser. This ticket builds
that proof surface. It is the foundation the whole run stands on.

## Problem

- `src/room.ts:3` imports the LLM module directly (`import * as llm`), so nothing can run
  `Room` without network access and an API key.
- `src/room.ts:47` drives ticks with `setInterval`; there is no way to advance the
  pipeline deterministically or to know when in-flight work has finished.
- There is no scenario test: nothing asserts that replaying a fixture through `Room`
  produces a valid canvas, emits utterances in order, or handles a bad op / a render failure.
- There is no offline report a human can skim to judge output quality.

## Solution direction

Two deliverables sharing one seam.

**The seam.** `Room` takes an LLM implementation; the real one is the default.
Define the interface in `src/llm.ts` from the functions that already exist there
(`tick`, `restructure`, `summarize`, `repair` — lines 40–66) and export the real
implementation as an object satisfying it. Keep the constructor signature backward
compatible: `new Room()` must still work everywhere it is used today.

Add one public method to `Room` that runs a single tick to completion and resolves
when any in-flight LLM work has finished — the existing `maybeTick` made callable
and awaitable. `start()`/`stop()` stay as they are. Do not otherwise change tick logic:
T3 rewrites it next wave and will keep this method's contract.

**Acceptance suite** — `test/scenarios.test.ts` with a stub LLM in `test/stub-llm.ts`.
The stub is scripted and deterministic: a sensible default (e.g. one markdown upsert per
call whose id and content derive from the utterances it was shown) plus a way for a test
to queue specific responses. Document the stub's surface in its file header — T3 and T7
will extend it. Scenarios must cover, without network or timers:

- each of the three fixtures replayed through `Room` → every utterance is emitted as an
  `utterance` message in order; final canvas is non-empty; every block passes
  `validateOp`; `rev` is monotonic.
- a queued malformed op → rejected, counted, the good ops in the same batch applied.
- `renderFailed(id, error)` with a queued repair → block replaced; with an empty queue →
  block deleted.
- an LLM call that throws → the utterances are retried on the next tick, not lost
  (see `src/room.ts:86-92`).

**Eval reports** — `src/eval.ts`, run as `npm run eval -- <fixture>`. Drives `Room` with
the real LLM, no server, no sleeping through `t_ms`. Writes
`evals/<fixture>-<timestamp>.md`: each block as a titled section with its source in a
fenced block (` ```mermaid ` or ` ```markdown `), then a summary line — LLM calls made,
ops applied, ops rejected with reasons, blocks by kind, wall time, token usage from
`response.usage`. Print the summary line to stdout. Add `evals/` to `.gitignore`.
Uses whichever `ROOMY_LLM` backend is configured (see `CLAUDE.md` → Run it); fail fast with a clear message if the transport errors.

Latitude: the shape of the stub API, how quiescence is tracked internally, the report's
exact layout. Not open: the seam must be a constructor argument, not a global or an env
switch; the acceptance suite must not touch the network under any configuration.
